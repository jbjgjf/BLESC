# インシデント対応手順

> 版 `pilot-protocol-v1` / 草案 / 承認前
> 実地演習は dry run day 3（[#168](https://github.com/jbjgjf/BLESC/issues/168)）で行う。**演習していない手順を本番の手順と呼ばない。**

## 0. 共通の原則

1. **止めることを先に考える。** 原因が分かる前でも、拡大を止める操作（収集停止、export停止）は先に打てる。
2. **本文をSlack・メール・Issueに貼らない。** 事故の記録に必要なのはid・件数・時刻であって、本人が書いた文章ではない。
3. **記録は事後に書き足さない。** 対応中に時刻と操作を書く。後からの再構成は、対応の質を実際より良く見せる。
4. **判断した人の名前を残す。** 「チームで判断した」は、誰も判断していない状態と区別がつかない。

## 1. 連絡体制

| 役割 | 担当 | 連絡手段 | 対応時間 |
| --- | --- | --- | --- |
| 研究責任者 | `DECISION REQUIRED` | | |
| データ管理責任者 | `DECISION REQUIRED` | | |
| 運用責任者 | `DECISION REQUIRED` | | |
| 学校側窓口 | `DECISION REQUIRED` | | |
| 校内の相談体制（SC/SSW等） | `DECISION REQUIRED` | | |

**決定者: 研究責任者と学校責任者。この表が埋まるまで募集を開始しない。** 危機記述への対応は §3 で「30分以内に連絡」と書いてあっても、連絡先が空欄なら手順ではない。

## 2. 重大度の区分

| 区分 | 定義 | 一次対応の目標 |
| --- | --- | --- |
| P0 | 生命・身体の危険、個人データの外部流出、他参加者のデータが見えている | 即時 |
| P1 | 同意前・撤回後の研究書き込み、外部AIへの送信、export内のPII | 当日中 |
| P2 | 保存失敗、欠測、通知の不達 | 翌営業日 |
| P3 | 表示崩れ、文言の誤り | 次のリリース |

**P0とP1は、原因調査より先に停止する。**

## 3. 危機的記述（自傷・他害・急迫した危険）

### 3.1 検知

収集専用モードのため、**外部AIによる自動判定は行わない**。検知は次の2経路のみ。

1. 運営者による目視レビュー（頻度は protocol D4 の `DECISION REQUIRED`）
2. 参加者本人・保護者・教職員からの申し出

### 3.2 手順

1. **読む。** 記述を運営者が確認する。判断を急がない。
2. **記録する。** 対応記録に research code・時刻・重大度の判断・判断者を書く。**本文は転記しない。**
3. **学校側窓口へ連絡する。** 目標: 覚知から30分以内（P0の場合）。連絡内容は「この研究コードの参加者について、校内の相談体制につないでほしい」まで。研究側が診断や評価を述べない。
4. **学校が本人へ接触する。** 研究側から直接、本人へ危機対応の連絡をしない（研究の説明に、そう書いていない限り）。
5. **参加継続の判断。** 学校責任者と研究責任者が、参加を続けるか一時停止するかを決める。本人の希望を最優先する。
6. **事後の記録。** 対応の完了時刻と結果を追記する。

### 3.3 してはいけないこと

- アプリの画面で、診断名・リスクスコア・危険度を本人に表示すること。
- 「AIが危険と判定した」と伝えること（判定していない）。
- 本文を、対応に必要のない人へ共有すること。
- 対応を理由に、本人の同意なく保護者へ本文を渡すこと。

## 4. 個人データの流出・混線

### 4.1 他参加者のデータが見えた（P0）

1. **収集を止める。** `pilot_studies.status` を `closed` にし、新規の書き込みを止める。
2. 影響範囲を確定する。「誰の何が、誰に、いつからいつまで見えたか」を、ログとRLSの設定から特定する。
3. データ管理責任者が、通知の要否を判断する（本人・保護者・学校・監督機関）。
4. 原因のRLSポリシーまたはクエリを修正し、`sentra/supabase/tests/` に**再発を検出するテストを追加**してから再開する。修正だけで再開しない。
5. 再開の判断は研究責任者・データ管理責任者・運用責任者の3名。

### 4.2 本文が外部AIへ送られた（P1）

1. 送信点を特定する（`collectionMode.ts` が列挙する5経路のどれか、または新設された6つ目）。
2. 該当参加者を特定し、件数を数える。
3. 送信先の事業者に対する削除依頼の可否を確認する。
4. 本人・保護者へ通知する。**「送られていない」と説明したものが送られたのだから、通知しない選択肢はない。**
5. `tests/collection-mode.test.mjs` が検出できなかった理由を調べ、テストを直す。

## 5. 保存の失敗（P2）

1. `submission_failures` の件数を確認する。参加者ごとの失敗数と時刻を出す。
2. 参加者側の表示を確認する。**参加者が「保存されなかった」と分かる状態になっているか。** 分かっていないなら、それはP1に上げる。
3. 再送を促す。再送で重複が生じていないことを `client_submission_id` の一意制約で確認する。
4. 期待提出数とDB件数の照合を行う（[#168](https://github.com/jbjgjf/BLESC/issues/168) の照合SQL）。

## 6. 同意前・撤回後の書き込み（P1）

1. 書き込みの範囲を特定する（research code、件数、時刻）。
2. 該当データを研究datasetから除外する。**削除ではなく除外を先に行う**（削除すると、何が起きたかの調査ができなくなる）。
3. 原因を特定し、状態遷移の検査を追加する。
4. 調査完了後、データ管理責任者の判断で削除する。
5. 本人・保護者へ通知する。

## 7. 鍵と秘密値

### 7.1 `RESEARCH_RAW_TEXT_KEY` の漏洩（P0）

1. 収集を止める。
2. 新しい鍵を発行し、`raw_text_key_version` を上げる。
3. 既存の暗号化列を新鍵で再暗号化する。**再暗号化中に平文をログへ出さない。**
4. 旧鍵を失効させる。
5. 漏洩の経路（GitHub、ログ、client bundle、error report）を特定し、そこに秘密値が入らない検査を足す。

### 7.2 鍵を失った場合

暗号化された本文は復号できない。**これは事故であって、削除ではない。** 参加者へ「保存したはずのデータが読めなくなった」ことを通知し、以後の解析から除外する。復元できると説明しない。

## 8. 事故の記録

事故ごとに次を残す。書式は [#168](https://github.com/jbjgjf/BLESC/issues/168) のevidence templateと共通にする。

| 項目 | 内容 |
| --- | --- |
| 覚知時刻 | 誰が、どうやって気づいたか |
| 重大度 | P0〜P3と、その判断者 |
| 影響範囲 | research code の件数（**本文は書かない**） |
| 一次対応 | 何を止めたか、時刻 |
| 原因 | 特定できたこと。できていないなら「未特定」と書く |
| 恒久対応 | 追加したテスト・修正のcommit SHA |
| 通知 | 誰に、いつ、何を伝えたか |
| 判断者 | 再開・継続・中止を決めた人の名前 |

**「未特定」と書ける欄を用意しておく。** 埋めなければならない欄しかないと、推測が原因欄に入る。
