# 合成→実データ移転研究：順位の移転の解析と封印

**Issue：** #215（凍結モデルの合成→実データ順位移転）。親 #210。コードは `sentra/backend/research_engine/transfer/`（`forecasting.py`・`ranking.py`・`seal.py`・`real_data.py`・`pipeline.py`）。
**状態：** 解析コードは実装済みで、合成データの上で最後まで走る。実データ側は「入力が来たら動く形」で止めてある（下の「実データ側の止め方」）。**この解析で使っている値はすべて dry run 用の仮置き**で、事前登録 P1〜P14 の提案ではない。

## 何を比べるか

翌日（1日先）の自己評定を、次の3つのモデルで予測します（#215・protocol §7.2 が最低限として挙げている比較対象）。

| モデル | 予測 |
|---|---|
| `persistence`（持続値） | 起点の日の値 |
| `train_mean`（訓練平均） | 当てはめ側のその項目の平均 |
| `linear_ar`（線形AR） | y(t+1) = a + b·y(t)。**連続する2日がともに観測された組だけ**で当てはめる |

事前登録した履歴モデル・文章モデル（P2）はまだありません。`Forecaster` の形に合わせれば同じ経路に足せます。

研究エンジン v0 の `dynamics/baselines.py` をそのまま使わない理由は2つです。(1) 翌日予測では「次の行」ではなく「次の日」が目標で、欠測日をまたぐ組は1日の遷移ではない。(2) v0 の線形ARは欠測を `nan_to_num` で0に置き換えて当てはめる。どちらも S1〜S5 では問題にならないが、日単位の欠測が多い日記では結果を変える。

**モデルの入力は `day_index` と `self_report` だけ**です（研究 export にある欄）。本文と提出時刻はモデルに渡りません。本文を置き換えても提出時刻を消しても予測が変わらないことを、漏洩検査が実行して確かめます。

## 2つの分割は混ぜない

| 分割 | 当てはめ | 採点 | 答える問い |
|---|---|---|---|
| `participant`（参加者分割） | train 側の参加者の全日 | heldout 側の参加者の全日（起点 1〜27日目） | 見たことのない人への汎化 |
| `temporal`（時間分割） | 全参加者の 1〜k 日目 | 全参加者の k+1〜28 日目の目標 | 知っている人の未来 |

- 参加者分割は研究エンジン v0 の `data.splits.participant_split` を再利用します（参加者単位・seed 固定・行の順序に依存しない）。validation 側は使っていません（チューニング予算 P2 が未決定）。
- 2つの結果は別々に出し、1つの数にまとめません（protocol §7.2）。まとめようとすると `split_kinds_mixed` で拒否します。
- 当てはめに入るのは `model_training_use` に同意した参加者だけです（同意ゲート #212）。

## 採点する点と、欠測による減少

ある起点の予測を採点するのは、**翌日の値が観測されていて、すべてのモデルが答えたとき**だけです。同じ点の集合で比べるためです。除いた点は理由ごとに数えます。

| 理由 | 意味 |
|---|---|
| `target_missing` | 翌日の値が無い（提出が無い、またはその項目を飛ばした） |
| `declined:origin_missing` | 起点の日の値が無い（`require_observed_origin` のとき） |
| `declined:no_history` | 起点までに観測が1つも無い |
| `below_inclusion_minimum` | 解析対象の最低条件（P5）を下回る参加者。dry run では0日（誰も除かない） |

合成と実で減り方が違えば、それ自体が順位が移転しない理由になりえます。比較の出力には両側の減少を並べます。

## 参加者単位の MAE と不確実性

1. 参加者ごとに、その人の採点点での MAE を出す。
2. モデルの MAE は、参加者の MAE の平均（採点点の多い人が重くならない）。
3. 区間は参加者を復元抽出する bootstrap。**モデル間の差は同じ抽出で両モデルを評価する対の区間**にする。
4. 同点域（P3）：dry run では「差の区間が0を含めば同点」。`margin`（差の絶対値が許容差未満）と、その両方の規則も実装してある。どれを使うかは P3。

## 順位の比較で報告するもの

分割ごと・予測目標ごとに、次をすべて出します。どれを主結果とするか（P3）と、何を失敗とするか（P7）は決めていないので、出力にも「未決定」と書きます。

- モデルの組ごとの分類：一致（`agree`）、逆転（`reversal`）、両側同点（`tie_both`）、合成側だけ同点、実側だけ同点
- 合成上の勝者が実側でも勝者か、実側の同点域にいるか
- **合成上の勝者が、実側で単純モデルに負けたか**（負けた場合も結果を残す）
- モデルごとの MAE と区間、組ごとの MAE 差と区間（合成・実の両方）
- 評価対象の減少（合成・実の両方）
- 当てはめ方ごとの別結果：`target_split`（実データ側で当てはめる＝実データでの学習）と `synthetic_frozen`（合成だけで当てはめ、実データは採点だけ）

## 封印

合成上の順位は、実データの採点より前に封印します（`seal.py`）。

- 封印ファイルは、順位の結果の全部、解析計画、合成データ・manifest・事前登録の hash、コードの commit を持つ。
- `ranking_hash` は順位の結果だけの hash で、同じコード・同じデータ・同じ計画なら同じ値になる（作り直して確かめられる）。`seal_hash` は封印日時を含む記録全体の hash。
- **書き込みは1回だけ。** 既にある封印ファイルを上書きしない。作り直した結果は別の結果として別の場所に置く。
- 比較は封印ファイルから読み戻した順位で行う（その場で計算し直さない）。
- 事前登録が凍結されていて、解析計画がその凍結から作られている場合だけ「確証解析に使える封印」になる。今作れる封印はすべて**候補（確証解析には使えない）**です。

hash は内容が同じことを確かめるだけで、改ざんは防ぎません。封印の意味は、ファイルの置き場所と書き込み権限、git の履歴で支えます。

## 実データ側の止め方

`real_data.score_real_export()` が実パイロットを採点する関数です。合成の dry run と同じ `evaluate_dataset`・`rank_evaluations`・`compare_rankings` を使います。次の順に確かめ、どれか1つでも欠ければ拒否します。

1. 必要な役割すべての承認記録（評価、実データで当てはめるなら当てはめも）
2. 凍結した事前登録
3. その凍結から作った解析計画（dry run の仮置き計画は拒否）
4. 確証解析に使える封印で、封印の後に変わっておらず、同じ事前登録・同じ計画の下で作られたもの
5. 同意ゲートと v0 契約

**5 は、1〜4 が揃っても今はすべての実データ行を拒否します**（`real_data_refused`）。これが「止めておく」です。サーバー側の同意確認ができ、v0 契約の変更がレビューされたとき、この関数は書いてあるとおりに動きます。

## 漏洩検査（実行するもの）

`leakage_probes()` は次を実際に実行し、確かめた件数と一緒に結果を出します。実行できなかった検査は「合格」にしません。

| 検査 | 内容 |
|---|---|
| `participant_split_disjoint` | 参加者分割で、当てはめ側と評価側に同じ参加者がいない |
| `temporal_fit_before_scored_targets` | 時間分割で、当てはめは k 日目まで、採点する目標は k+1 日目から |
| `inputs_precede_targets` | 全予測で、モデルに渡した入力の最終日 ≤ 起点 < 目標（翌日）。入力の最終日は**実際に渡した長さ**で測る |
| `future_values_do_not_move_earlier_forecasts` | ある日より後の値をすべて変えて予測し直しても、それ以前を起点とする予測（全モデル）が変わらない |
| `text_and_timestamps_are_not_inputs` | 本文を置き換え、提出時刻を消しても予測が同じ |
| `generation_truth_refused_as_input` | 生成真値を含むオブジェクトを渡すと拒否される |
| `split_kinds_not_pooled` | 2つの分割をまとめようとすると拒否される |

入力が起点の翌日まで見えてしまう不具合を、テストで意図的に入れると、上の2つの検査が赤になることも確かめています。

## 実行

```bash
cd sentra/backend
python -m research_engine.transfer.cli dry-run --seed <seed> --out <出力先>
```

選択用の合成コホートと、**実パイロットの代わりに置いた2つ目の合成コホート**（`simulated_real_stand_in`。実データではなく、実データの予想でもない）を作り、漏洩検査・同意ゲートの dry run・合成上の順位・封印・2つ目のコホートでの順位・封印した順位との比較・測定の監査を出します。
