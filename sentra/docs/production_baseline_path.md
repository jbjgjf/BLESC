# The production baseline path — one contract, two stores

Raised as three items in an architecture review: a split datastore, an LLM that
defaulted to mock, and no anomaly detection during cold start. Only the first
was a live defect. This document records what was actually wrong, because the
shape of it was materially different from the report.

## What the review reported, and what was there

| reported | actual |
| --- | --- |
| SQLite and Supabase can drift, so baselines and displayed data disagree | They cannot drift, because they never met. The FastAPI backend is not called in production at all. |
| `USE_MOCK_LLM` defaults to `"true"` | Fixed in `2770986` (June 2026). `os.getenv("USE_MOCK_LLM", "")` — the default is not-mock, and an OpenAI key takes priority. |
| Cold start blocks detection below two entries | The threshold is fourteen **days**, not two entries, and the block is deliberate (#91). |

## The actual defect

`NEXT_PUBLIC_API_URL` is unset on Vercel, so `api/client.ts` posts to `/api` —
the Next.js route handler — and never to FastAPI. Every write lands in Supabase.
The backend's `daily_feature_aggregations` table therefore stays empty in
production, and `MIN_REFLECTION_BASELINE_DAYS` gates on rows that are never
written. The fourteen-day ramp could not complete for any student, ever.

What ran instead, in `app/api/entries/route.ts`:

```
anomaly_score = 1 + triggers * 0.8 - protective * 0.25 + relations * 0.05
z_scores_json = { trigger_count, protective_count, relation_count }
```

An arithmetic function of a single submission. It had no history, so it could
not measure deviation from anything; its floor was 1.0, so a day identical to
every other day still read as a signal; and it moved with how much a student
wrote. It was written to `insights.anomaly_score` and rendered to the student as
"Hybrid Reflection Signal". Its `z_scores_json` held raw counts under a name
asserting they had been divided by a standard deviation.

The route handler recorded the truth in the adjacent column the whole time —
`baseline_deviation_json: { baseline_available: false, reason: "single
production submission" }`. Nothing read it. This is the same failure mode as
#106, where every stored row claimed to be a temporal baseline and no row could
contradict it.

**Two consequences that outlived the score itself.** `longitudinal_features`
accumulated the value as `latest_anomaly_score`, so the fabricated number became
a time series — which reads as far stronger evidence than any single value in
it. And `PERSIST_ANOMALY_SCORE = False`, the retention decision of 2026-08-06
(`educator_display_policy.md`), was honoured only by the backend. Production
went on writing a risk score attached to an identifiable minor for the two
months after new writes were supposed to have stopped.

## What ships

The baseline computation is ported to `frontend/src/lib/baseline.ts` and runs in
`api/client.ts`, the only place holding both the database connection and the
participant id. Supabase needs no aggregation table: the daily feature vector is
a pure function of nodes and relations, and those are in `graph_snapshots`.

Both implementations are pinned to `shared/baseline_conformance.json`, whose
expected values are generated by running the backend
(`backend/scripts/generate_baseline_conformance.py`) and checked by
`frontend/tests/baseline.test.mjs` and `backend/tests/test_baseline_conformance.py`.
Two implementations of one contract is what produced #106; a shared fixture set
is what stops it recurring.

Below fourteen days production now writes the same `not_enough_data` explanation
the backend writes. No score, no z-scores, and `baseline_provenance` carrying
`days_remaining` so the UI can say 「基準値の学習中（残り N 日）」.

### A port, not an integration

This does not merge the two datastores. FastAPI still owns SQLite and still
serves the research and evaluation pipelines; Supabase is the production store.
What is now guaranteed is that the two cannot disagree about what a baseline
*is*. Consolidating the stores is a larger change — the backend has no Postgres
driver, and its SQLModel tables and the Supabase migrations are different
schemas with different row-level security — and is not attempted here.

The cost is a second implementation to keep in step. The conformance contract is
what makes that cost bounded: a divergence fails a build rather than reaching a
student.

## Reading old rows

`hasSettledBaseline()` in `api/client.ts` gates every read on
`baseline_deviation_json.baseline_available === true`, and is positive-only: a
row counts as a measurement when it says so, not when it fails to say otherwise.
Every row written before this change fails that test, so the old fabricated
scores stop rendering immediately rather than aging out. The rows themselves are
untouched — deleting them is irreversible and waits on the same legal advice as
the retention question.

## On the cold-start item

The review asked for anomaly detection during the ramp. That is what `2770986`
built — "0 days → population defaults; 1-13 days → blended" — and what `930473a`
(#91) deleted after an external review found the eleven population constants had
never been measured. `baseline_reestimation.md` records the trade and
pre-registers the sample floors any replacement would have to clear.

Reinstating it was declined. The real cold-start problem was the opposite of the
one reported: production was not withholding a reading during the ramp, it was
emitting a fabricated one on day one *and* on day one hundred. Fixing the
datastore split fixes the cold start, by making the ramp visible and honest
rather than by filling it with numbers nobody measured.

## Still open

- `event_avg_duration` carries weight 0.08 in the deviation table and is always
  zero on this path: the production extraction schema never asks the model for a
  node `duration`, though the backend's does. It is reported in
  `degenerate_features` rather than left looking measured (cf. #85), but the
  asymmetry between the two schemas is real and unfixed.
- `isolation_signal` accumulates only for a Behavior node labelled exactly
  `"isolation"`. Anything in Japanese, or "social isolation", scores zero. Ported
  faithfully because changing it changes both sides at once; pinned in the
  contract so the brittleness is visible.
- The deviation weights themselves remain unvalidated against any outcome
  (M-02). This work makes the z-scores honest as *deviation from this student's
  own typical*. It says nothing about whether deviation predicts anything.
