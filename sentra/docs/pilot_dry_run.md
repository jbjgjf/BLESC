# パイロット dry run 手順書（#168）

この手順書は、本番相当環境で成人スタッフと合成本文だけを使い、10アカウント × 3日を短縮実行するためのものです。実在の生徒・保護者の連絡先や本文は使いません。実際の募集開始は、研究責任者・データ管理責任者・運用責任者の3名が結果を確認して Go と署名するまで行いません。

## 役割と確認リンクの受け渡し

保護者確認リンクは BLESC から保護者へ直接送信しません。学校だけが、研究で承認済みの連絡経路を使って保護者へ届けます。

1. 運用担当者が、本人の assent が記録済みの minor だけを対象に管理 API で確認リンクを発行する。
2. 運用担当者は token 本文を運用台帳へ保存せず、研究コード、発行時刻、有効期限、学校への受渡時刻、受渡担当者だけを記録する。
3. 学校担当者へリンクを安全な経路で渡す。通常のチャット、Issue、PR、スクリーンショットには貼らない。
4. 学校担当者が、学校で登録済みの保護者連絡先へリンクを届ける。BLESC 側へ保護者のメールアドレス・電話番号を転記しない。
5. 保護者は本人とは別の端末またはブラウザでリンクを開き、説明文書の version と対象の研究を確認して「同意する」または「同意しない」を選ぶ。
6. 学校担当者は配達不能・宛先不明・辞退を運用担当者へ戻す。参加者本人にリンクを渡して自己確認させない。
7. 運用担当者は管理画面/APIで `verified` / `declined` / 未回答 / 期限切れを照合する。未回答や期限切れの minor は収集へ進めない。再発行時は旧リンクを失効させる。

dry run では、学校担当役と保護者役を別の成人スタッフが担当し、リンクが参加者役の画面に一度も表示されないこと、期限切れリンクが一般化されたエラーになること、辞退後に収集が開かないことを証拠に残します。

## 事前準備

- deployment SHA、環境名、実施者、開始時刻を evidence template に記録する。
- 10個の専用テストアカウントを用意し、adult正常、minor+guardian正常、invite期限切れ、invite二重利用、同意拒否、保護者未確認、途中撤回、offline→retry、二重送信、危機的記述運用演習を1つずつ割り当てる。
- 招待コードと保護者リンクは本番参加者用と分離し、短い有効期限を設定する。
- ブラウザ E2E は `cd sentra && supabase start && supabase db reset`、続いて `cd frontend && npm ci && npx playwright install chromium && npm run test:e2e` で実行する。
- `sentra/docs/evidence/pilot-enrollment/` の6画面と Playwright HTML report を証拠として保管する。token、cookie、メールアドレスが写っていないことを確認する。

## 3日短縮実行

### Day 0 — 登録と権限

- 招待発行、login、説明文書 version、本人 assent、adult の保護者不要経路を確認する。
- minor は保護者未確認のまま `/journal` を直打ちし、参加登録画面へ戻ることを確認する。
- 上記の学校経由で保護者役へリンクを届け、別端末で回答する。本人画面から保護者回答を変更できないことを確認する。
- 期限切れ、二重利用、decline の表示と、別 user による read/write 拒否を確認する。

### Day 1 — 提出と検知

- 正常提出、AI endpoint 0-call、保存成功、dashboard/DB/export 件数を照合する。
- offline→retry と二重送信を行い、参加者と運営者の双方で失敗を検知でき、再送後も重複がないことを確認する。
- synthetic な危機的記述で連絡手順だけを演習し、実在人物への連絡や緊急通報は行わない。

### Day 2/3 — 撤回、export、復旧

- 途中撤回後の画面遷移と次回提出の API 拒否を確認する。
- 期待提出数と DB/export/dashboard を照合し、PII review と retention purge を実行する。
- delete/withdraw/export/retention/crisis runbook と復旧を実地演習する。

## Go / No-Go

理由不明の欠測、cross-user read/write、外部AI送信、同意前・保護者未確認・撤回後の研究書込、再送後の重複のいずれかが1件でもあれば No-Go とし、対応 Issue を作成します。未解決 P0 は0件、P1 は研究責任者が理由付きで受容したものだけとします。Discussion #137 に deployment SHA、件数、逸脱、Issue、Go/No-Go、3名の署名を記録します。自動テストの成功は、人間による3日運用と署名の代わりにはなりません。
